# DDL Pipeline + Interaktywny HTML — Specyfikacja

> Rozszerzenie narzędzia `apex_export_to_md` o parsowanie plików SQL DDL/PL/SQL, generowanie dokumentacji bazy danych (MD human + LLM) z diagramem Mermaid ER oraz interaktywną stronę HTML łączącą dane APEX z bazą danych.

## 1. Cel

Automatyczne generowanie pełnej dokumentacji projektu Oracle APEX:
- Dokumentacja bazy danych (tabele, widoki, pakiety PL/SQL, sekwencje) w dwóch formatach MD
- Diagram relacji tabel (Mermaid ER w MD + interaktywny graf w HTML)
- Interaktywna strona HTML do przeglądania i nawigacji między elementami APEX a obiektami bazy danych

## 2. Parser SQL DDL

### 2.1 Zakres obsługiwanych obiektów

| Obiekt | Źródło w SQL | Wyciągane dane |
|--------|-------------|----------------|
| Tabela | `CREATE TABLE` | nazwa, kolumny (typ, nullable, default, identity) |
| Constraint PK | `CREATE TABLE` (inline) lub `ALTER TABLE ... ADD CONSTRAINT ... PRIMARY KEY` | nazwa, kolumny |
| Constraint FK | `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY ... REFERENCES` | nazwa, kolumny, tabela referencyjna, kolumny referencyjne |
| Constraint UNIQUE | `CREATE TABLE` (inline) lub `ALTER TABLE ... ADD CONSTRAINT ... UNIQUE` | nazwa, kolumny |
| Constraint CHECK | `CREATE TABLE` (inline `CHECK(...)`) | nazwa, wyrażenie |
| Indeks | `CREATE [UNIQUE] INDEX` | nazwa, tabela, kolumny, unique |
| Sekwencja | `CREATE SEQUENCE` | nazwa, min/max, increment, start, cache |
| Widok | `CREATE [OR REPLACE] [FORCE] [EDITIONABLE] VIEW` | nazwa, lista kolumn, zapytanie SQL |
| Package spec | `CREATE [OR REPLACE] PACKAGE ... AS ... END;` | nazwa, procedury, funkcje (parametry, typy zwracane), stałe, komentarze |
| Package body | `CREATE [OR REPLACE] PACKAGE BODY ... AS ... END;` | nazwa, pełny kod z komentarzami, procedury/funkcje z opisami |
| Komentarz tabeli/widoku | `COMMENT ON TABLE` | tekst komentarza (uwaga: Oracle używa `COMMENT ON TABLE` także dla widoków — parser rozróżnia po nazwie obiektu) |
| Komentarz kolumny | `COMMENT ON COLUMN` | tabela, kolumna, tekst |

### 2.2 Podejście: regex-based parser

1. **Podział na bloki** — dwuetapowy:
   - Najpierw wydziel bloki PL/SQL (od `CREATE.*PACKAGE` do `/` na osobnej linii) — separator: `/`
   - Następnie podziel resztę na bloki DDL — separator: `;`, ale **z uwzględnieniem stringów**: splitter śledzi stan wewnątrz `'...'` (single-quoted literals) i nie dzieli na `;` wewnątrz stringów. Jest to konieczne, bo `COMMENT ON TABLE` może zawierać wieloliniowe zapytania SQL z `;` wewnątrz tekstu komentarza.
   - Implementacja: prosty automat stanowy (state machine) z flagą `in_quote` przełączaną na każdy apostrof `'`. Podwójny apostrof `''` (escape w Oracle) nie zmienia stanu.
2. **Klasyfikacja bloków** — regex na początku bloku (`CREATE TABLE`, `ALTER TABLE`, `CREATE.*PACKAGE`, itd.)
3. **Ekstrakcja danych** — dedykowany regex per typ obiektu
4. **Deduplikacja** — strategia "first-wins": pierwszy napotkany `CREATE INDEX`, `COMMENT ON` itp. jest zachowywany, kolejne identyczne (ta sama nazwa obiektu) są pomijane. Uzasadnienie: pierwsze wystąpienie jest zwykle najbardziej kompletne w eksportach Oracle SQL Workshop.
5. **Tolerancja błędów** — malformowane bloki (np. niekompletny `CREATE INDEX` bez listy kolumn) są pomijane z ostrzeżeniem w logu, nie powodują przerwania parsowania.
6. **Komentarze w PL/SQL** — zachowane w kodzie źródłowym; dodatkowo parsowane jako opisy:
   - `--` przed `PROCEDURE`/`FUNCTION` → opis procedury/funkcji
   - `--` w linii parametru → opis parametru
   - bloki `-- =====` → separatory logiczne

### 2.3 Wiele plików SQL

Parser automatycznie wykrywa `*.sql` w katalogu eksportu. Jeśli jest wiele plików, wszystkie są parsowane i łączone w jeden model `DbSchema`. Opcja CLI `--ddl-files` pozwala wskazać konkretne pliki.

### 2.4 Szczegóły parsowania kolumn

Regex kolumn musi obsługiwać:
- Typy bez parametrów: `CLOB`, `DATE`, `NUMBER`
- Typy z parametrami: `VARCHAR2(4000 CHAR)`, `NUMBER(11,0)`, `TIMESTAMP (6)`
- Klauzulę `IDENTITY`: `GENERATED BY DEFAULT ON NULL AS IDENTITY ...` — parser wykrywa wzorzec `GENERATED.*AS IDENTITY` i ustawia `identity=True`, pomijając szczegółowe parametry (MINVALUE, MAXVALUE, itp.)
- Defaults: `DEFAULT 'Otwarty'`, `DEFAULT SYSDATE`, `DEFAULT 0`

## 3. Model danych (db_models.py)

```python
@dataclass
class DbColumn:
    name: str
    data_type: str                    # np. "VARCHAR2(4000 CHAR)", "NUMBER(11,0)"
    nullable: bool = True
    default: str | None = None        # np. "'Otwarty'", "SYSDATE"
    identity: bool = False
    comment: str | None = None

@dataclass
class DbConstraint:
    name: str
    constraint_type: str              # "PK", "FK", "UQ", "CHK"
    columns: list[str] = field(default_factory=list)
    ref_table: str | None = None      # tylko FK
    ref_columns: list[str] = field(default_factory=list)  # tylko FK
    check_expression: str | None = None  # tylko CHK

@dataclass
class DbIndex:
    name: str
    table_name: str
    columns: list[str] = field(default_factory=list)
    unique: bool = False

@dataclass
class DbTable:
    name: str
    columns: list[DbColumn] = field(default_factory=list)
    constraints: list[DbConstraint] = field(default_factory=list)
    indexes: list[DbIndex] = field(default_factory=list)
    comment: str | None = None

@dataclass
class DbView:
    name: str
    columns: list[str] = field(default_factory=list)
    sql: str = ""
    comment: str | None = None

@dataclass
class DbSequence:
    name: str
    min_value: str | None = None
    max_value: str | None = None
    increment_by: str | None = None
    start_with: str | None = None
    cache: str | None = None

@dataclass
class DbParameter:
    name: str
    data_type: str
    direction: str = "IN"             # "IN", "OUT", "IN OUT"
    description: str | None = None

@dataclass
class DbSubprogram:
    name: str
    subprogram_type: str              # "PROCEDURE" lub "FUNCTION"
    parameters: list[DbParameter] = field(default_factory=list)
    return_type: str | None = None    # tylko dla FUNCTION
    description: str | None = None    # z komentarza nad procedurą/funkcją
    visibility: str = "public"        # "public" (w spec) lub "private" (tylko w body)

@dataclass
class DbPackage:
    name: str
    spec_subprograms: list[DbSubprogram] = field(default_factory=list)
    body_subprograms: list[DbSubprogram] = field(default_factory=list)
    constants: list[str] = field(default_factory=list)
    spec_source: str = ""             # kod specyfikacji
    body_source: str = ""             # kod body z komentarzami

@dataclass
class DbSchema:
    tables: list[DbTable] = field(default_factory=list)
    views: list[DbView] = field(default_factory=list)
    packages: list[DbPackage] = field(default_factory=list)
    sequences: list[DbSequence] = field(default_factory=list)
```

## 5. Diagram Mermaid ER

Generowany automatycznie z FK constraints i osadzany w `*_db_human.md`.

### Reguły generowania

- Relacje z `DbConstraint` typu FK
- Kardynalność: strona PK = `||`, strona FK = `o{` (zakładamy jeden-do-wielu)
- Każda tabela pokazuje max 5 kolumn: PK + FK + kolumny z constraint'ami
- Tabele bez FK (izolowane) renderowane jako samodzielne bloki
- Nazwy relacji: nazwa constraint FK

## 6. Linker APEX ↔ Baza danych (apex_db_linker.py)

### Cel

Automatyczne wykrywanie powiązań między stronami APEX a obiektami bazy danych.

### Algorytm

1. **Zbierz nazwy obiektów DB** — zbiór nazw tabel i widoków z `DbSchema`
2. **Przeskanuj źródła SQL w APEX** — dla każdej strony:
   - `region.source` (zapytania SQL regionów)
   - `process.source` (kod PL/SQL procesów)
   - `validation.plsql_expression` / `validation.sql_expression`
   - LOV-y (zapytania w shared components)
3. **Dopasowanie** — regex szuka wzorców z word boundaries (`\b`) aby uniknąć false-positive (np. `B_AUDYT` nie matchuje `B_AUDYT_KONTROLA`):
   - `FROM\s+\b{table_name}\b`
   - `JOIN\s+\b{table_name}\b`
   - `INTO\s+\b{table_name}\b`
   - `UPDATE\s+\b{table_name}\b`
   - `INSERT\s+INTO\s+\b{table_name}\b`
   - `DELETE\s+FROM\s+\b{table_name}\b`
   - Dopasowanie case-insensitive
   - Kolejność dopasowania: od najdłuższych nazw do najkrótszych (aby `B_AUDYT_KONTROLA` matchował przed `B_AUDYT`)
4. **Wynik** — mapa `dict[str, set[str]]`: page_id → zbiór nazw tabel/widoków

### Model

```python
@dataclass
class ApexDbLink:
    page_id: int
    page_name: str
    db_objects: list[str]       # nazwy tabel/widoków
    source_type: str            # "region", "process", "validation", "lov"
    source_name: str            # nazwa regionu/procesu
```

## 7. Interaktywny HTML (html_renderer.py)

### 7.1 Format

Jeden self-contained plik HTML (~500-800 KB, z czego ~300-500 KB to vis.js minified). Cały CSS, JS (vis.js) i dane JSON inline. Działa offline bez serwera.

### 7.2 Struktura

```
┌──────────────────────────────────────────────┐
│  [Logo TR] SKW Documentation     [szukaj...] │
├──────────────────────────────────────────────┤
│  [Diagram]  [Baza danych]  [APEX ↔ DB]      │
├──────────────────────────────────────────────┤
│                                              │
│           (aktywna zakładka)                 │
│                                              │
├──────────────────────────────────────────────┤
│  apex_export_to_md | Tomasz Rembiasz         │
│  Współpraca: Claude (Anthropic)              │
└──────────────────────────────────────────────┘
```

### 7.3 Zakładka: Diagram relacji

- **Rendering:** vis.js Network graph
- **Węzły:** prostokąty z nazwą tabeli, kolor wg kategorii:
  - Biznesowe (B_AUDYT, B_KONTROLA, B_ANKIETA, B_OCENA): niebieski
  - Słownikowe (B_SL_*): zielony
  - Techniczne (B_IMPORT_LOG, B_*_HIST, B_*_TMP): szary
- **Krawędzie:** FK, kierunek od child do parent, label = nazwa FK
- **Interakcja:**
  - Kliknięcie węzła → panel boczny z pełnymi detalami tabeli
  - Hover → tooltip: komentarz + liczba kolumn
  - Zoom/pan/drag
  - Przycisk "Reset layout"

### 7.4 Zakładka: Przeglądarka bazy danych

- **Panel lewy:** drzewo obiektów (Tabele / Widoki / Pakiety / Sekwencje)
- **Panel główny:** szczegóły wybranego obiektu
  - Tabela: kolumny, constraints, indeksy, powiązania FK (in/out), komentarze
  - Widok: zapytanie SQL z podświetleniem składni (inline CSS), kolumny
  - Pakiet: lista procedur/funkcji z opisami, rozwijany pełny kod z komentarzami
  - Sekwencja: parametry
- **Wyszukiwarka:** filtruje obiekty po nazwie, kolumnie, komentarzu

### 7.5 Zakładka: Mapa APEX ↔ Baza danych

- **Dwie kolumny:** strony APEX (lewa) | obiekty DB (prawa)
- **Kliknięcie strony APEX** → podświetla powiązane tabele/widoki po prawej
- **Kliknięcie tabeli** → podświetla strony APEX po lewej
- **Linie połączeń** — SVG/Canvas lines między powiązanymi elementami
- Dane z `ApexDbLinker`

### 7.6 Branding

- **Logo:** inline SVG — stylizowane inicjały "TR" w geometrycznym okręgu, kolorystyka granatowy (#1a365d) + złoty (#d4a843)
- **Nagłówek:** logo + "{App Name} — Dokumentacja projektu"
- **Stopka:** "Wygenerowano narzędziem apex_export_to_md | Autor: Tomasz Rembiasz | Współpraca: Claude (Anthropic)"

## 8. Integracja z istniejącym narzędziem

### 8.1 Nowe argumenty CLI

### 8.2 Nowe pola w AppConfig

```python
enable_ddl: bool = True
ddl_files: list[str] = field(default_factory=list)
enable_html: bool = True
html_output: str = ""
author_name: str = "Tomasz Rembiasz"
```

### 8.3 Rozszerzony pipeline

```python
def run_pipeline(config):
    # --- Istniejący pipeline APEX (bez zmian) ---
    app = parse_apex(...)
    render_apex_md(app, config)

    # --- Nowy pipeline DDL ---
    sql_files = find_sql_files(input_path, config)
    if sql_files and config.enable_ddl:
        schema = parse_ddl_files(sql_files)
        render_db_md(schema, config)         # human + llm

        # --- Nowy pipeline HTML ---
        if config.enable_html:
            links = link_apex_db(app, schema)
            render_html(app, schema, links, config)
```
